# أبو عزت TV | AboEzzat Receiver for Windows

الهدف هو نقل تجربة وإمكانيات **AboEzzat Receiver Android** إلى Windows، ثم بناء تطبيقات مستقلة لـ LG webOS وSamsung Tizen، مع إبقاء مستودعي Android Receiver وAboEzzat Cast الأصليين دون تعديل.

## الحالة الحالية — 27 نوفمبر 2026

يوجد فرع Windows النشط:
`feature/libvlc-header-playback`

تم إنشاء تطبيق Windows باستخدام **WPF و.NET 8 وLibVLC**. أحدث بناء مكتمل ومتحقق منه هو تشغيل GitHub Actions رقم **84** (Run ID: **45970631865**) على commit `e17e1a21dd9faf2d86c41aacf5fde0048a11c67e`:

https://github.com/mohamedezzat19/AboEzzat-TV/actions/runs/45970631865

تحققت من نجاح Checkout وSetup .NET 8 وRestore وPublish Windows x64 وInno Setup وإنشاء Setup.exe ورفع Artifact. اسم الملف `AboEzzat-TV-Windows-Setup`، وحجم الـArtifact المضغوط 131,573,455 بايت، ومعرّفه 15185286004، وبصمة SHA-256 المسجلة `54c7345e1d404c257e3ecbd54eae6392a142b401a59921287d2f948282f18c17`. رُفع في 27 نوفمبر 2026 وصلاحيته حتى 25 فبراير 2027. نجاح البناء ورفع الملف لا يثبت تثبيته أو نجاح التشغيل والاتصال على جهاز Windows.

التعديل الحالي يفصل قبول TCP عن تحليل HTTP: حلقة القبول تسجل ترتيب كل اتصال وتضعه في طابور محدود سعته 32 عميلًا، بينما تعالج 8 مهام تحليل الطلبات بالتوازي. لكل عميل مهلة قراءة 15 ثانية وحد أقصى لجسم الطلب 1 MiB. يحمل كل طلب رقم ترتيب القبول الأصلي، ويستخدمه Windows لمنع طلب وسائط أقدم أو أمر إيقاف متأخر من تجاوز عملية أحدث حتى لو انتهى تحليل الاتصالات بترتيب مختلف. هذا يقلل أثر العميل الصامت على قبول الاتصالات، لكنه ما زال يحتاج اختبار ضغط وتكامل فعلي.

## تحديث واجهة المشغل — 27 نوفمبر 2026

أضيفت في commits `f00a62b5` و`1abf65ed` و`25858cec` و`28b0d677` و`e17e1a21` تحسينات لواجهة التشغيل: شريط تقدم سفلي بمؤشر أزرق، أزرار الرجوع 10 ثوانٍ والتشغيل/الإيقاف المؤقت والتقديم 10 ثوانٍ في الوسط، والتحكم بالصوت يسارًا، وأزرار الإعدادات والترجمة والتنزيل والتكرار يمينًا. أضيفت أوضاع التكرار: إيقاف، تكرار الفيديو الحالي، وتكرار قائمة Cast. زر التنزيل المباشر يقبل حاليًا امتدادات ملفات معروفة فقط؛ لا يدعم تنزيل HLS أو DASH أو البث الحي. أصبح زر الترجمة يحتفظ بعرض `CC` المختصر بعد البحث، وتم مسح ترويسات الفيديو والصوت القديمة عند الانتقال إلى الصور. هذه التغييرات اجتازت البناء #84، لكنها لم تُختبر على جهاز Windows فعلي.

## الموجود في كود Windows الحالي

- واجهة WPF عربية بملء الشاشة مع عناصر تحكم للفيديو.
- خادم HTTP مخصص باسم `TcpHttpListener` مبني مباشرة فوق `.NET TcpListener`، يستمع على كل واجهات IPv4 المحلية على المنفذ 8081، ويستقبل `POST /play` وروابط query. لا يستخدم Windows HTTP.sys ولا يحتاج URLACL.
- حلقة قبول TCP مستقلة عن تحليل HTTP، مع 8 محللات متزامنة وطابور انتظار محدود سعته 32 عميلًا.
- قاعدة جدار حماية Windows للاتصالات الواردة على TCP 8081 ضمن ملف تعريف Private.
- إعلان اكتشاف UDP multicast على `239.255.42.99:37020`.
- استقبال رابط فيديو ورابط صوت منفصل وتشغيلهما عبر LibVLC.
- دعم قائمة Cast متعددة العناصر: العنصر الأول يصل عبر `POST /play` والعناصر التالية عبر `GET /?queue=<URL-encoded>`. يحتفظ Windows بما يصل إلى 100 رابط فيديو HTTP(S)، ويرتبها حسب رقم قبول TCP، ويشغل التالي تلقائيًا عند انتهاء الحالي؛ وأوامر `prev` و`next` تتنقل داخل قائمة Cast قبل سجل المشاهدة.
- استقبال الصور وقائمة صور وعرض شرائح بفواصل زمنية.
- سجل تشغيل ومواضع استكمال مشاهدة محفوظة محليًا.
- متصفح داخلي مبني على WebView2، مع شريط عنوان وأزرار رجوع/تقدم/تحديث/الرئيسية.
- زر بحث يدوي عن ترجمة عربية، مع رمز `CC` مختصر بعد انتهاء البحث.
- أوضاع تكرار `Off / One / Playlist`، وزر تنزيل مباشر للملفات ذات الامتدادات المعروفة فقط؛ قوائم HLS وDASH والبث الحي غير مدعومة بالتنزيل حاليًا.
- واجهة تشغيل محدثة: أزرار النقل في الوسط، الصوت يسارًا، والإعدادات والترجمة والتنزيل والتكرار يمينًا.
- أوامر الريموت المطابقة لـ AboEzzat Cast: `stop` و`play_pause` و`rw` و`ff` و`prev` و`next` و`volume_up` و`volume_down` و`mute` (ويقبل المستقبل أيضًا الاسم البديل `previous`).

هذه قدرات موجودة في الشيفرة وليست كلها مختبرة عمليًا بعد.

## توافق بروتوكول AboEzzat Cast — ما تمت مراجعته

تمت مراجعة مسارات الإرسال في مستودع AboEzzat Cast:
- `POST /play` مع JSON يحتوي `url` و/أو `audio`.
- `GET /?url=...` لإرسال رابط مباشر.
- `GET /?command=ping` للتحقق من اتصال المستقبل.
- أوامر الريموت تُرسل كـ `GET /?command=...`.
- البحث اليدوي عن المستقبل في Cast يحاول فتح اتصال TCP على المنفذ 8081.

كود Windows الحالي يحتوي مقابلات لهذه المسارات والأوامر. هذه مراجعة ساكنة للكود وليست اختبار تكامل بين جهازين.

## تمرير ترويسات الوسائط — موجودة في الكود ومشمولة في البناء 84

بعد البناء 70 أُضيفت في فرع Windows طبقة Proxy محلية على loopback لتجاوز محدودية خيارات HTTP في LibVLC. عند وجود ترويسات إضافية غير User-Agent وReferer، يمرّر Windows طلبات الفيديو والصوت والصور عبر هذه الطبقة، بما يشمل Origin وCookie وAccept وAccept-Language والترويسات المخصصة المسموح بها. كما تمرّر Range وIf-Range لطلبات الوسائط المباشرة، وتعيد كتابة روابط قوائم HLS النسبية وروابط URI داخل الوسوم حتى تمرّ قوائم الجودة والمقاطع ومفاتيح التشفير وخرائط التهيئة عبر نفس الجلسة.

ضوابط الأمان: لا تُمرّر Cookie إلا إذا طابق أصل رابط الوسائط أصل `Origin` أو `Referer` المرسل؛ لذلك لا تُرسل Cookies الخاصة بموقع مثل YouTube أو Instagram إلى نطاق CDN مختلف لمجرد أن الرابط النهائي عليه. تُقيّد Authorization ومفاتيح API بأصل رابط الوسائط، وتُحذف الترويسات الحساسة عند الانتقال إلى أصل آخر. لا تُسجّل قيم الترويسات الحساسة. إذا كان مزوّد البث يتطلب Cookie على CDN مختلف، فذلك يحتاج سياسة نطاق موثقة ومحددة بدل إرسال Cookie عشوائيًا.

طبقة Proxy موجودة في `windows/MediaHeaderProxy.cs`، وأُصلح خطأ التجميع الأول بإضافة `using System.IO` في commit `95c431e5`. شملها بناء Windows رقم 84 على commit `e17e1a21`، وتم إنشاء ورفع المثبّت. طبقة Proxy الحالية تدعم HTTP/HTTPS وGET/HEAD وRange وإعادة كتابة روابط HLS؛ إعادة كتابة DASH/MPD والاختبارات الوظيفية الفعلية ما زالت غير موجودة. التشغيل الإضافي [Windows installer verification #8](https://github.com/mohamedezzat19/AboEzzat-TV/actions/runs/45970631911) نجح أيضًا، لكنه ينفذ Restore/Publish/إنشاء المثبّت ورفع Artifact مرة أخرى، وليس اختبارًا وظيفيًا للـProxy.

## إعداد الاستماع والشبكة

يستخدم التطبيق `TcpHttpListener` المبني على `TcpListener` مباشرة؛ لا يحتاج URLACL أو HTTP.sys. المثبّت يضيف قاعدة جدار حماية خاصة لـ TCP 8081 فقط. إذا تعذر بدء الخدمة، تحقق أن المنفذ 8081 غير مستخدم وأن الشبكة مصنفة Private.

لا تفتح المنفذ على الإنترنت العام؛ الاستخدام المقصود هو شبكة LAN موثوقة.

## فجوات معروفة قبل إعلان التوافق

- طبقة Proxy المحلية لتمرير الترويسات الإضافية إلى HTTP/HTTPS وHLS اجتازت التجميع والنشر وإنشاء المثبّت في البناء 84، لكن لم تُختبر بعد على روابط بث فعلية. يلزم التحقق من Origin وCookie وAccept وAccept-Language وRange؛ كما أن DASH/MPD وإدارة Set-Cookie عبر نطاقات CDN ليست مكتملة.
- حد قائمة HLS البالغ 4 MiB يُفحص حاليًا بعد `ReadAsByteArrayAsync`؛ لذلك لا يمنع تحميل قائمة أكبر بالكامل إلى الذاكرة قبل رفضها. يجب تطبيق الحد أثناء القراءة.
- حماية SSRF في `MediaHeaderProxy` غير مكتملة: فحص الوجهات الحالي يقصر المخطط على HTTP/HTTPS، لكنه لا يمنع loopback أو عناوين الشبكات الخاصة في التحويلات وروابط HLS التابعة. يلزم وضع سياسة وجهات آمنة تراعي مصادر LAN التي يرسلها المستخدم عمدًا.
- لا يوجد حتى الآن مشروع اختبارات وظيفية لـMediaHeaderProxy؛ Workflow المسمى `Windows installer verification` ينفذ بناء المثبّت مرة أخرى ولا يختبر الترويسات أو Range أو HLS.
- طابور Cast متعدد العناصر أصبح مدعومًا في Windows فقط: أول عنصر عبر `POST /play` ثم العناصر التالية عبر `GET /?queue=...`، بحد أقصى 100 رابط فيديو HTTP(S). تُرتب العناصر حسب رقم قبول TCP وتُشغّل تباعًا. طابور الصور المختلط بالفيديو غير مدعوم بعد؛ يلزم اختبار الإرسال المتعدد الفعلي من الهاتف.
- التزامن بين مسار الفيديو ومسار الصوت المنفصل موجود في كود Windows، لكنه يحتاج اختبارًا على ملفات وروابط حقيقية.
- فحص نوع بعض روابط CDN غير ذات الامتداد يستخدم طلب HEAD اختياريًا في مهمة منفصلة؛ وآخر تعديل يحافظ على روابط الصور عديمة الامتداد داخل مصفوفة الصور. يحتاج ذلك اختبارًا فعليًا مع روابط CDN متتابعة.
- المتصفح الداخلي مبني على WebView2، والمثبّت يفحص وجود Microsoft Edge WebView2 Runtime ويعرض رابط Microsoft الرسمي إذا لم يُكتشف. ما زال تشغيل المتصفح بعد التثبيت واختباره على جهاز Windows مطلوبين.
- الإعدادات الحالية أساسية وليست مطابقة بالكامل لإعدادات Android. صورة الترحيب والأيقونة تُنزّلان عند أول اتصال بالإنترنت وتُخزّنان محليًا، وليستا مضمّنتين داخل المثبّت.
- لا توجد بعد اختبارات تكامل آلية تثبت اتصال AboEzzat Cast بالتطبيق.
- لم يتم اختبار MP4 أو HLS أو الصوت المنفصل أو الصور أو قائمة Cast متعددة العناصر أو أوامر الريموت على جهاز Windows فعلي حتى الآن.
- قبول الاتصالات وتحليل الطلبات أصبحا منفصلين مع تزامن محدود وترتيب قبول محفوظ؛ يلزم اختبار عدة عملاء صامتين بالتوازي مع إرسال وسائط فعلية للتأكد من عدم تأخر Cast أو تجاوز الطلبات القديمة.

## التثبيت والاختبار المطلوبان

1. أحدث بناء مكتمل هو تشغيل GitHub Actions رقم 84. نزّل Artifact باسم `AboEzzat-TV-Windows-Setup` من [صفحة التشغيل 84](https://github.com/mohamedezzat19/AboEzzat-TV/actions/runs/45970631865).
2. يتضمن Artifact رقم 84 دعم قائمة Cast متعددة العناصر، وقبول TCP المستقل وتحليل HTTP المتوازي المحدود، وWebView2، وطبقة Proxy لتمرير ترويسات الوسائط إلى HTTP/HTTPS وHLS، وتحديثات واجهة المشغل وأوضاع التكرار والتنزيل المباشر للملفات المدعومة. حجم الـArtifact المضغوط 131,573,455 بايت.
3. فك ضغط الـArtifact وشغّل `AboEzzat-TV-Setup.exe` على Windows x64. إذا لم يكن WebView2 Runtime موجودًا، اتبع رابط Microsoft الرسمي الذي يعرضه المثبّت.
4. وافق على قاعدة جدار الحماية للشبكة الخاصة، ولا تفتح المنفذ على الإنترنت العام.
5. وصّل الكمبيوتر والهاتف على الشبكة المحلية نفسها.
6. اختبر ظهور AboEzzat TV داخل AboEzzat Cast، ثم أرسل صورة، وفيديو MP4، ورابط HLS، وفيديو بصوت منفصل، ورابطًا يحتاج Headers.
7. افتح عدة اتصالات TCP صامتة بالتوازي، ثم أرسل فيديو وصورة وأمر إيقاف من Cast؛ تأكد أن الاتصالات الصامتة لا توقف القبول، وأن أحدث عملية وسائط صحيحة هي التي تنفذ.
8. أرسل اختيارًا متعددًا من Cast، وتأكد أن العنصر الأول يبدأ فورًا وأن العناصر اللاحقة تُضاف بالترتيب وتعمل تلقائيًا عند نهاية كل فيديو.
9. اختبر أوامر الريموت، خصوصًا `prev` و`next` داخل القائمة، وسجّل أي فشل مع نوع الرابط ورسالة الخطأ.

## الفروع والمنصات

- `feature/libvlc-header-playback`: تطبيق Windows WPF الحالي.
- `main`: يحتوي نموذج Electron الأقدم، وليس نفس نسخة Windows WPF الحالية.
- LG webOS وSamsung Tizen: لم تُبنَ لهما تطبيقات بعد؛ يحتاج كل نظام تطبيقًا وحل استقبال/اكتشاف متوافقًا مع قيودهما. لا يُعد مثبت Windows تطبيقًا صالحًا للتثبيت على التلفزيون.
